# راه‌اندازی LocalCast روی Headscale شخصی شما

**English version: [README.md](README.md)**

این پوشه یک سرور Headscale کامل و آمادهٔ استقرار است، برای کسانی که نمی‌خواهند مسیر پیش‌فرض
LocalCast به سرور هماهنگ‌کنندهٔ شرکت Tailscale وابسته باشد.

همهٔ آنچه اینجاست اختیاری است. حالت پیش‌فرض LocalCast به هیچ‌کدام از این‌ها نیاز ندارد.

فایل‌های این پوشه:

| فایل | چیست |
|------|------|
| `README.md` / `README.fa.md` | همین راهنما |
| `docker-compose.yml` | Headscale و Caddy، با نسخهٔ پین‌شده و توضیح خط‌به‌خط |
| `config.yaml` | پیکربندی سرور Headscale؛ `setup.sh` از آن به‌عنوان الگو استفاده می‌کند |
| `Caddyfile` | پروکسی معکوسی که TLS کنترل‌پلین را پایان می‌دهد |
| `setup.sh` | بخش‌های ۳ و ۴ را برای شما انجام می‌دهد و دو مقداری را که LocalCast می‌خواهد چاپ می‌کند |

## ۱. این چیست، و آن یک کاری که نمی‌تواند بکند

Headscale یک پیاده‌سازی متن‌باز از **سرور هماهنگ‌کنندهٔ** Tailscale است. این سرور، دفترچهٔ نشانی و
واسطهٔ تبادل کلید یک شبکهٔ مِش WireGuard است: تصمیم می‌گیرد چه دستگاه‌هایی عضو شبکهٔ شما هستند،
نشانی `100.x` هر کدام را می‌دهد، و به آن‌ها می‌گوید چطور همدیگر را پیدا کنند. دادهٔ شما از آن عبور
نمی‌کند. وقتی دو دستگاه از وجود هم باخبر شدند، بایت‌های ویدیو مستقیماً روی WireGuard بین آن دو
جریان پیدا می‌کند، یا اگر مسیر مستقیم باز نشود از طریق یک رله.

سرور شخصی یعنی فهرست دستگاه‌های شما روی ماشینی است که خودتان اجاره کرده‌اید، نه روی ماشین
Tailscale. تمام فایدهٔ کار همین است، و برای بعضی‌ها همین تمام ماجراست.

### این را پیش از هر کار دیگری بخوانید

**Headscale نمی‌تواند برای سرور LocalCast شما گواهی HTTPS صادر کند.**

در حالت پیش‌فرض LocalCast اصلاً به گواهی فکر نمی‌کنید. سرور هماهنگ‌کنندهٔ Tailscale نقطهٔ پایانی‌ای
به نام `/machine/set-dns` را پیاده کرده است که به یک گره اجازه می‌دهد از کنترل‌پلین بخواهد رکورد
چالش ACME DNS-01 را از طرف او منتشر کند. به همین دلیل `tailscale cert` یک گواهی واقعی و مورد
اعتماد عمومی از Let's Encrypt برای `yourmachine.tailXXXX.ts.net` برمی‌گرداند، بدون هیچ تنظیمی.

Headscale آن نقطهٔ پایانی را پیاده نکرده است. این تنظیمی نیست که از قلم انداخته باشید و نسخه‌ای
نیست که لازم باشد به آن ارتقا دهید — تا نسخهٔ پایدار فعلی، اصلاً وجود ندارد. در تاریخ ۲۰۲۶-۰۹-۰۱
مستقیماً از مخزن بالادستی بررسی شد:

- [juanfont/headscale#2527 — «tailscale cert + serve tracking»](https://github.com/juanfont/headscale/issues/2527)
  — **باز**، ثبت‌شده در ۲۰۲۵-۰۴-۱۴، آخرین فعالیت ۲۰۲۶-۰۸-۳۱، هدف‌گذاری روی نسخهٔ **v0.34**. خلاصهٔ
  خودِ نگه‌دارنده از کار باقی‌مانده: مدیریت رکوردهای DNS برای دامنهٔ پایه، افزودن `/machine/set-dns`،
  پشتیبانی از `DNSConfig.CertDomains` و نوسازی مدیریت گواهی. تازه‌ترین نظر روی این ایشو
  (۲۰۲۶-۰۸-۳۱) از یک نمونهٔ اولیهٔ **داخلی** با پشتیبانی Azure DNS حرف می‌زند، نه از قابلیتی که
  ادغام شده باشد.
- [juanfont/headscale#2137 — «\[Feature\] tailscale cert»](https://github.com/juanfont/headscale/issues/2137)
  — **باز**، ثبت‌شده در ۲۰۲۴-۰۹-۱۶، هدف‌گذاری روی **v0.34**.
- [juanfont/headscale#2696 — «Implement tailscale cert PoC»](https://github.com/juanfont/headscale/pull/2696)
  — یک pull request **باز و ادغام‌نشده**.
- نسخهٔ پایدار فعلی **v0.29.3** است (۲۰۲۶-۰۷-۲۹). نسخهٔ v0.34 چهار نسخهٔ فرعی جلوتر است و تاریخ
  مشخصی ندارد.

قابلیت **Funnel** — انتشار یک سرویس روی اینترنت عمومی بدون port forward — سرویسی است که Tailscale
اجرا می‌کند، نه یک ویژگی پروتکل، و به همین ترتیب در دسترس نیست:
[juanfont/headscale#1040](https://github.com/juanfont/headscale/issues/1040) با وضعیت
**بسته‌شده، بدون برنامه برای پیاده‌سازی** ثبت شده است. LocalCast این را اعمال می‌کند: انتخاب
هم‌زمان حالت «سرور شخصی» و Funnel در همان فرم تنظیمات رد می‌شود، نه بعداً.

**در عمل یعنی چه:** پس از پایان این راهنما یک مِش خصوصی کارآمد دارید، اما هنوز باید انتخاب کنید که
LocalCast *چگونه* گواهی خود را بگیرد. بخش ۵ دو گزینهٔ صادقانه پیش رویتان می‌گذارد. هیچ‌کدام سخت
نیست، اما نمی‌توانید از انتخاب فرار کنید، و LocalCast اجازه نمی‌دهد پیکربندی‌ای را ذخیره کنید که
نمی‌تواند گواهی تولید کند.

> اگر این متن را ماه‌ها بعد می‌خوانید، اول همان لینک‌های ایشو را باز کنید. اگر Headscale پشتیبانی از
> `tailscale cert` را منتشر کرده باشد، بخش ۵ منسوخ است و محدودیت `certStrategy: 'control-plane'`
> در LocalCast باید بازنگری شود.

## ۲. پیش‌نیازها

### یک سرور

Headscale یک باینری کوچک Go با پایگاه‌دادهٔ SQLite است. هماهنگ می‌کند؛ ویدیوی شما را رله نمی‌کند.
بار کاری‌اش ناچیز است.

| | |
|---|---|
| CPU / RAM | یک هستهٔ مجازی و ۱ گیگابایت رم راحت است. با ۵۱۲ مگابایت هم کار می‌کند. |
| دیسک | ۱۰ گیگابایت. پایگاه‌دادهٔ یک خانوار در حد چند مگابایت است. |
| سیستم‌عامل | هر لینوکس به‌روزی با Docker. Debian 12/13 و Ubuntu 24.04 کم‌دردسرترین‌اند. |
| شبکه | یک **IPv4 عمومی و ثابت**. پشت NAT نباشد. |

ارزان‌ترین پلن هر ارائه‌دهنده‌ای کافی است. برای پهنای‌باندی که مصرف نمی‌کنید پول ندهید — مگر آنکه
در بخش ۵ راهبرد `external-proxy` را انتخاب کنید، که در آن صورت هشدار پهنای‌باند همان بخش را
**پیش از** انتخاب پلن بخوانید.

### یک نام دامنه

به **دو نام** نیاز دارید و باید با هم فرق داشته باشند:

| کاربرد | نمونه | توضیح |
|---|---|---|
| کنترل‌پلین | `headscale.example.com` | عمومی. به VPS اشاره می‌کند. همین می‌شود `controlUrl` در LocalCast. |
| پایهٔ MagicDNS | `net.example.com` | هرگز به‌صورت عمومی resolve نمی‌شود. پسوند نام هر دستگاه می‌شود. |

اگر این دو یکی باشند Headscale اجرا نمی‌شود، و دلیلش واقعی است: `headscale.example.com` باید روی
اینترنت عمومی به VPS شما resolve شود، در حالی که `*.net.example.com` باید به نشانی‌های `100.x`
داخل شبکه resolve شود و فقط برای اعضای همان شبکه. یک نام نمی‌تواند هر دو کار را بکند.

سرور LocalCast شما در نهایت `localcast.net.example.com` خواهد شد.

از دامنه‌ای استفاده کنید که واقعاً در ثبت‌کننده در اختیار دارید، نه زیردامنهٔ رایگان یک سرویس
dynamic-DNS. اگر بعداً راهبرد `dns01` را انتخاب کنید، به دسترسی API برای ویرایش رکوردهای آن نیاز
خواهید داشت.

### رکوردهای DNS

یک رکورد، پیش از اجرای هر چیزی:

</div>

```
headscale.example.com.   A      203.0.113.10      # IPv4 عمومی سرور شما
headscale.example.com.   AAAA   2001:db8::10      # اختیاری، اگر VPS شما IPv6 دارد
```

<div dir="rtl">

پیش از ادامه صبر کنید تا واقعاً resolve شود:

</div>

```bash
dig +short headscale.example.com
```

<div dir="rtl">

اگر چیزی چاپ نکرد، Let's Encrypt شکست می‌خورد و شما یک ساعت Caddy را مقصر می‌دانید.

**برای `net.example.com` هیچ رکورد DNS نسازید.** MagicDNS داخل شبکهٔ خصوصی زندگی می‌کند.

### پورت‌های VPS

| پورت | پروتکل | لازم؟ | چرا |
|---|---|---|---|
| 80 | TCP | **بله** | چالش ACME HTTP-01 و هدایت HTTP به HTTPS. |
| 443 | TCP | **بله** | خود کنترل‌پلین. |
| 443 | UDP | خیر | HTTP/3. باز گذاشتنش ضرری ندارد و کمی سریع‌تر است. |
| 22 | TCP | بله | دسترسی SSH خودتان. خودتان را بیرون نگذارید. |
| 3478 | UDP | خیر | فقط اگر بعداً رلهٔ DERP توکار را فعال کنید. این پیکربندی نمی‌کند. |

یک اشتباه رایج: بستن پورت ۸۰ بعد از صدور گواهی. تمدید تقریباً هر ۶۰ روز اتفاق می‌افتد و از همان
چالش استفاده می‌کند. بی‌صدا شکست می‌خورد، و حدود یک ماه بعد همهٔ دستگاه‌ها یکباره دیگر به
کنترل‌پلین شما اعتماد نمی‌کنند.

### ابزارها

`docker` (نسخهٔ ۲۰.۱۰ به بالا همراه افزونهٔ Compose v2)، `jq` و یک ویرایشگر متن. اسکریپت راه‌اندازی
همه را بررسی می‌کند و نبودشان را با نام اعلام می‌کند.

## ۳. استقرار

این پوشه را روی VPS کپی کنید. فایل‌ها را بخوانید. بعد اسکریپت را اجرا کنید — یا دستی انجام دهید؛
اسکریپت کاری فراتر از مراحل دستی نمی‌کند.

</div>

```bash
scp -r docs/headscale/ you@203.0.113.10:~/headscale
ssh you@203.0.113.10
cd ~/headscale
less docker-compose.yml config.yaml Caddyfile setup.sh   # واقعاً بخوانیدشان
```

<div dir="rtl">

در این پروژه عمداً هیچ دستور `curl … | bash` وجود ندارد. اسکریپتی که واسطهٔ هویت شبکهٔ خانهٔ شما را
راه می‌اندازد، اسکریپتی است که اول می‌خوانیدش.

### با اسکریپت

</div>

```bash
chmod +x setup.sh
./setup.sh
```

<div dir="rtl">

دامنهٔ کنترل‌پلین، دامنهٔ پایهٔ MagicDNS، یک نشانی ایمیل برای اعلان‌های انقضای Let's Encrypt و یک نام
کاربری Headscale را می‌پرسد. سپس پیکربندی را می‌نویسد، استک را بالا می‌آورد، کاربر را می‌سازد، یک
کلید پیش‌احراز صادر می‌کند و دو مقداری را که در LocalCast می‌چسبانید چاپ می‌کند.

اجرای دوباره‌اش امن است. وجود `config/config.yaml` را تشخیص می‌دهد و پیشنهاد می‌کند از آن استفادهٔ
دوباره کند، کاربر تکراری نمی‌سازد، و تنها کاری که همیشه انجام می‌دهد صدور یک کلید تازه است — چون
Headscale کلیدها را درهم‌سازی‌شده ذخیره می‌کند و نمی‌تواند کلید قبلی را دوباره نشان دهد.

اگر خروجی را به فایل هدایت کنید، از چاپ کلید خودداری می‌کند. این عمدی است: یک کلید پیش‌احراز، یک
ماشین را در شبکهٔ شما ثبت می‌کند و جایش در فایل لاگ نیست.

### دستی

</div>

```bash
mkdir -p config lib caddy/data caddy/config

# ۱. رندر پیکربندی: فقط این دو تنظیم زنده را عوض کنید.
cp config.yaml config/config.yaml
$EDITOR config/config.yaml
#   server_url: https://headscale.example.com
#   dns.base_domain: net.example.com

# ۲. به Caddy بگویید برای کدام دامنه گواهی بگیرد.
cat > .env <<'EOF'
HEADSCALE_DOMAIN=headscale.example.com
ACME_EMAIL=you@example.com
EOF

# ۳. بالا آوردن.
docker compose up -d
docker compose logs -f caddy      # رسیدن گواهی را ببینید، بعد Ctrl-C
```

<div dir="rtl">

### دربارهٔ نسخهٔ پین‌شده

فایل `docker-compose.yml` روی `docker.io/headscale/headscale:v0.29.3` و `caddy:2.11.4-alpine` پین
شده است. نه `latest` و نه `stable`.

Headscale رابط خط فرمانش را بین نسخه‌های فرعی طوری تغییر می‌دهد که اسکریپت‌ها را می‌شکند. دو نمونهٔ
واقعی: در نسخهٔ 0.26 پرچم `--user` در `preauthkeys` دیگر نام کاربری را نپذیرفت و شناسهٔ عددی خواست؛
در 0.28 دستورهای `preauthkeys expire` و `delete` از `--user <name> <key>` به `--id <ID>` منتقل
شدند. یک تگ شناور، یکی از این تغییرها را شبی اعمال می‌کند که شما حواستان نیست، و خرابی طوری به
نظر می‌رسد که انگار اسکریپت خودتان ایراد دارد.

برای ارتقای بعدی، [راهنمای ارتقای بالادستی](https://headscale.net/stable/setup/upgrade/) را
بخوانید، اول از `lib/` نسخهٔ پشتیبان بگیرید، و هر بار فقط یک نسخهٔ فرعی پایدار جلو بروید.

فایل compose، خلاصهٔ (digest) مانیفست نسخهٔ v0.29.3 را هم در یک توضیح دارد، اگر پین تغییرناپذیر را
به تگ ترجیح می‌دهید.

## ۴. کاربر، کلید، و اینکه هر مقدار کجا می‌رود

Headscale دستگاه‌ها را زیر یک **کاربر** گروه‌بندی می‌کند. برای یک خانوار این یعنی یک کاربر — اپراتور
— و همهٔ دستگاه‌ها به آن تعلق دارند. یک **کلید پیش‌احراز** به دستگاه اجازه می‌دهد بدون ورود از طریق
مرورگر ثبت شود، و دقیقاً همین چیزی است که LocalCast لازم دارد: `netedge` بدون رابط گرافیکی درون
پروسهٔ Electron اجرا می‌شود و کسی نیست که روی صفحهٔ تأیید کلیک کند.

</div>

```bash
# ساخت کاربر (یک‌بار).
docker compose exec headscale headscale users create home

# پیدا کردن شناسهٔ عددی. از نسخهٔ 0.26 دستور بعدی شناسه می‌خواهد، نه نام.
docker compose exec headscale headscale users list
# ID | Name | Username | Email | Created
# 1  |      | home     |       | 2026-09-01 ...
#
# ستون مورد نظر شما Username است؛ «Name» نام نمایشی اختیاری است و اگر
# ‑‑display-name نداده باشید خالی است. شکل ماشین‌خوان:
#   docker compose exec -T headscale headscale users list --output json | jq

# صدور یک کلید یک‌بارمصرف با اعتبار ۲۴ ساعت.
docker compose exec headscale headscale preauthkeys create --user 1 --expiration 24h
# hskey-auth-AbCdEfGhIjKl-<۶۴ نویسهٔ دیگر>
```

<div dir="rtl">

اگر به‌جای شناسه نام کاربری بدهید این خطا را می‌گیرید:
`Error: invalid argument "home" for "-u, --user" flag: strconv.ParseUint: parsing "home": invalid syntax`.
این همان پرچمِ تغییرکرده است، نه نصب خراب.

> **کلید فقط یک‌بار نمایش داده می‌شود.** Headscale یک درهم‌سازی bcrypt از آن نگه می‌دارد. از آن پس
> `headscale preauthkeys list` مقدار `hskey-auth-AbCdEfGhIjKl-***` را نشان می‌دهد — به اندازهٔ
> شناسایی کلید، نه به اندازهٔ استفاده از آن. اگر مقدار را پیش از چسباندن گم کردید، یکی دیگر صادر
> کنید؛ راه بازیابی وجود ندارد و هیچ چیز خراب نشده است.

پرچم‌هایی که ارزش دانستن دارند:

| پرچم | اثر |
|---|---|
| `--expiration 24h` | تا کِی هنوز می‌توان با این کلید *ثبت‌نام* کرد. پیش‌فرض `1h`. هیچ ربطی به مدت اتصال دستگاه ندارد. |
| `--reusable` | اجازه می‌دهد چند دستگاه با یک کلید ثبت شوند. راحت است، و آن‌گاه یک رشتهٔ لو رفته هر تعداد ماشین را راه می‌دهد. برای LocalCast خاموش بگذاریدش. |
| `--ephemeral` | گره با قطع اتصال حذف می‌شود. برای سرور LocalCast **هرگز**. |

### داخل LocalCast

روی ماشین ویندوز، LocalCast را باز کنید، به **«تنظیمات» ← «سرور هماهنگ‌کننده شبکه»** بروید و از
**«پیش‌فرض»** به **«سرور شخصی»** تغییر دهید.

| فیلد در صفحه | کلید پیکربندی | چه چیزی وارد کنید | نمونه |
|---|---|---|---|
| «آدرس سرور» | `controlUrl` | دقیقاً همان `server_url`. با `https://`، بدون اسلش پایانی، بدون مسیر. | `https://headscale.example.com` |
| «کلید احراز هویت» | `authKey` | کل رشتهٔ `hskey-auth-…`. | `hskey-auth-AbCdEfGhIjKl-…` |
| «نام دستگاه» | `hostname` | نامی که این ماشین در شبکه می‌گیرد. | `localcast` |
| «روش گواهی» | `certStrategy` | `external-proxy` یا `dns01` — **بخش ۵**. | |
| «دامنهٔ گواهی» | `certDomain` | نامی که گواهی برای آن است. به راهبرد بستگی دارد. | |
| «انتشار» | `expose` | باید روی «فقط شبکهٔ خصوصی» (`tailnet`) بماند. Funnel اینجا وجود ندارد. | |

دو کاری که فرم اجازه نمی‌دهد انجام دهید، و این‌ها حفاظ‌اند نه محدودیت:

- **`certStrategy: control-plane` در حالت شخصی** رد می‌شود — *«Headscale cannot issue certificates
  through the control plane; choose external-proxy or dns01.»* یعنی همان بخش ۱.
- **`expose: funnel` در حالت شخصی** رد می‌شود — *«Funnel is a Tailscale service and is not
  available on a self-hosted control server.»*

پیش از **«ذخیره»**، دکمهٔ **«آزمایش اتصال»** را بزنید. این آزمون یک اجرای خشک است: هم بررسی می‌کند
که سرور کنترل در دسترس است و هم اینکه راهبرد گواهی واقعاً می‌تواند گواهی تولید کند. پیکربندی‌ای که
نمی‌تواند کار کند همان‌جا که هنوز به فرم نگاه می‌کنید رد می‌شود، به‌جای اینکه به یک چرخندهٔ همیشگی
«در حال اتصال…» تبدیل شود.

مقدار `authKey` پیش از رسیدن به دیسک با DPAPI ویندوز رمزگذاری می‌شود و هرگز در لاگ نوشته نمی‌شود.

## ۵. TLS — و اینجا دو گواهی متفاوت در کار است

بیشتر استقرارهای شخصی همین‌جا خراب می‌شوند، پس دقیق باشیم که صحبت از کدام گواهی است.

**گواهی الف — گواهی کنترل‌پلین.** برای `https://headscale.example.com`. همان Caddy در
`docker-compose.yml` آن را خودکار با HTTP-01 می‌گیرد و تمدید می‌کند. چیزی برای تصمیم‌گیری نیست.
بدون آن، کلاینت‌های Tailscale اصلاً با سرور کنترل حرف نمی‌زنند.

**گواهی ب — گواهی خود LocalCast.** برای نامی که آیفون شما در مرورگر باز می‌کند. در حالت پیش‌فرض
Tailscale این را رایگان تحویل می‌دهد. Headscale نمی‌تواند (بخش ۱). این همان گواهی‌ای است که باید
برایش راهبرد انتخاب کنید.

باقی این بخش فقط دربارهٔ گواهی ب است.

### گزینهٔ ۱ — `external-proxy`: یک پروکسی معکوس جلوی LocalCast

**اگر می‌خواهید همین امروز کار کند، این را انتخاب کنید.** پروکسی‌ای که خودتان کنترل می‌کنید TLS را
پایان می‌دهد و HTTP ساده را روی شبکهٔ خصوصی به LocalCast می‌فرستد. طبیعی‌ترین جا برای این پروکسی
همان VPS‌ای است که تازه ساخته‌اید: IP عمومی دارد، پورت ۴۴۳ بازش است، و Caddy‌ای دارد که بلد است
گواهی بگیرد.

۱. Tailscale را روی VPS نصب و به Headscale خودتان وصل کنید. ترجیحاً از مخزن بستهٔ توزیع خودتان؛
   صفحهٔ [tailscale.com/download/linux](https://tailscale.com/download/linux) مراحل apt و dnf
   را دارد. Tailscale نصب‌کنندهٔ لوله‌ای هم منتشر می‌کند؛ مال خودشان است و امضا شده، اما باز هم
   اسکریپتی از اینترنت است که با دسترسی root اجرا می‌شود، پس اگر از آن استفاده می‌کنید اول
   بخوانیدش (`curl -fsSL https://tailscale.com/install.sh | less`).

</div>

```bash
sudo tailscale up --login-server https://headscale.example.com --authkey hskey-auth-…
```

<div dir="rtl">

۲. یک رکورد A بسازید: `localcast.example.com` به IP عمومی VPS.
۳. بلوک دوم سایت را در انتهای `Caddyfile` از حالت توضیح خارج کنید، نشانی `100.x` مربوط به LocalCast
را در آن بگذارید و `docker compose restart caddy` را اجرا کنید.
۴. در LocalCast: `certStrategy` برابر `external-proxy` و `certDomain` برابر `localcast.example.com`.

**معاوضه، در یک جمله:** از این پس هر بایتی که پخش می‌کنید مسیر گوشی ← VPS ← WireGuard ← رایانهٔ خانه
و برگشت را طی می‌کند، پس جابه‌جا شدن در یک فیلم 4K به سقف پهنای‌باند خروجی VPS محدود می‌شود و از
سهمیهٔ ترافیک آن کم می‌کند.

### گزینهٔ ۲ — `dns01`: گواهی دست خودِ LocalCast

**اگر واقعاً ویدیوی بزرگ پخش می‌کنید، این را انتخاب کنید.** LocalCast کلاینت ACME خودش را اجرا
می‌کند و مالکیت دامنه را با نوشتن یک رکورد TXT از طریق API ارائه‌دهندهٔ DNS شما اثبات می‌کند. هیچ
چیز عمومی لازم نیست به ماشین ویندوز برسد، و مسیر رسانه نظیربه‌نظیر روی WireGuard باقی می‌ماند.

۱. یک ارائه‌دهندهٔ پشتیبانی‌شده انتخاب کنید — LocalCast این‌ها را پیاده کرده است: `cloudflare`،
   `digitalocean`، `route53` و `gandi` — و مطمئن شوید `example.com` روی همان میزبانی می‌شود.
۲. یک توکن API با محدودترین دامنهٔ دسترسی ممکن بسازید: ویرایش رکوردهای DNS همان یک zone، نه چیز
   دیگری.
۳. در LocalCast: `certStrategy` برابر `dns01`، `certDomain` برابر `localcast.net.example.com`
   (یعنی `hostname` به‌علاوهٔ `base_domain` شما)، و `dnsProvider` و `dnsApiToken` طبق بالا.
۴. LocalCast گواهی را می‌گیرد، کَش می‌کند و خودش تمدید می‌کند. توکن هم مثل کلید احراز، رمزگذاری‌شده
   با DPAPI ذخیره می‌شود.

**معاوضه، در یک جمله:** باید توکنی نگه دارید که می‌تواند zone دی‌ان‌اس شما را ویرایش کند و این یک
اعتبارنامهٔ واقعی روی یک ماشین خانگی است — در عوض، مسیر ویدیو مستقیم است و VPS جز ترافیک هماهنگی
چیزی حمل نمی‌کند.

### انتخاب

| | `external-proxy` | `dns01` |
|---|---|---|
| زحمت راه‌اندازی | کم | متوسط |
| اعتبارنامهٔ اضافه | ندارد | یک توکن API دی‌ان‌اس |
| مسیر رسانه | از داخل VPS | مستقیم، نظیربه‌نظیر |
| جابه‌جایی در ویدیوی 4K | محدود به خروجی VPS | محدود به آپلود خانگی شما |
| هزینهٔ پهنای‌باند VPS | به اندازهٔ آنچه تماشا می‌کنید | ناچیز |

با `external-proxy` شروع کنید تا مطمئن شوید کل زنجیره کار می‌کند، و اگر پخش کند بود به `dns01`
بروید. جابه‌جایی بین این دو یک تغییر تنظیمات است، نه نصب دوباره.

می‌شوند و دانستن اینکه کدام‌یک شکسته ارزش دارد.

## ۷. برگشتن به سرور هماهنگ‌کنندهٔ پیش‌فرض

**«تنظیمات» ← «سرور هماهنگ‌کننده شبکه»** را باز کنید، **«پیش‌فرض»** را انتخاب کنید، آزمایش کنید،
ذخیره کنید.

کل رویه همین است. LocalCast سطر `network_config` جدید را می‌نویسد، گرهٔ tsnet را درون همان پروسهٔ
`netedge` که در حال اجراست دوباره راه می‌اندازد، و به هیچ چیز دیگری دست نمی‌زند.

**چه چیزی باقی می‌ماند، چون پایگاه‌دادهٔ SQLite اصلاً درگیر این تغییر نیست:**

| | |
|---|---|
| دستگاه‌های جفت‌شده | باقی می‌مانند — هیچ دستگاهی دوباره جفت نمی‌شود و هیچ QR ای دوباره اسکن نمی‌شود |
| ماتریس دسترسی | باقی می‌ماند — هر سطر `(دستگاه، پوشه) ← full/stream/none` دست‌نخورده است |
| پوشه‌های اشتراکی | باقی می‌مانند، با برچسب، پرچم نوشتنی و نمایهٔ فایل‌ها |
| چاپگرها و تاریخچهٔ چاپ | باقی می‌مانند |
| گذرواژه‌های WebDAV | باقی می‌مانند |
| گزارش فعالیت | باقی می‌ماند |

**چه چیزی عوض می‌شود:** نام میزبان سرور. در حالت پیش‌فرض چیزی شبیه `localcast.tailXXXX.ts.net`
می‌شود و روی Headscale شخصی `localcast.net.example.com` بود. کلاینت‌ها از پسش برمی‌آیند: رکورد
جفت‌شدنی که ذخیره کرده‌اند یک هویت است نه یک نشانی، و از طریق آن دوباره resolve می‌کنند.

**کارهایی که به‌هرحال بهتر است بکنید:**

- در حالت پیش‌فرض، راهبرد گواهی به `control-plane` برمی‌گردد. این درست است — Tailscale صادرش
  می‌کند. اگر `dnsApiToken` داشتید، دیگر استفاده نمی‌شود.
- هر دستگاه باید اپلیکیشن Tailscale‌اش به *همان* سرور کنترلی اشاره کند که LocalCast دارد. گوشی‌ای
  که هنوز به Headscale شما وارد است، LocalCast‌ای را که به شبکهٔ پیش‌فرض رفته نمی‌بیند. برگرداندن
  گوشی روی دسکتاپ با `tailscale switch` انجام می‌شود، و در اپ iOS با خروج و ورود دوباره.
- تا وقتی مطمئن نشده‌اید VPS را روشن نگه دارید. برگشتن هم همان سه کلیک در جهت عکس است و Headscale
  شما هنوز گره را ثبت‌شده دارد.

اگر برای همیشه کار Headscale تمام است، `docker compose down` متوقفش می‌کند و
`docker compose down -v && rm -rf lib caddy` نابودش. پوشهٔ `lib/` تمام سرور است — `db.sqlite` به
همراه `noise_private.key` — پس اگر کوچک‌ترین احتمالی هست که دوباره بخواهیدش، پیش از حذف جایی
کپی‌اش کنید.

## ۸. وقتی کار نمی‌کند

### گره هرگز در `headscale nodes list` ظاهر نمی‌شود

کلاینت `Success.` می‌گوید و بعد هیچ چیز روی سرور پیدا نمی‌شود.

- **پروکسی معکوس، ارتقای پروتکل را می‌بلعد.** پروتکل کنترلی Tailscale یک درخواست `POST` را به
  اتصالی با سرآیند `Upgrade: tailscale-control-protocol` ارتقا می‌دهد. Caddy ارتقاهای دلخواه را
  شفاف پروکسی می‌کند و به همین دلیل `Caddyfile` این پوشه به هیچ دستور websocket نیاز ندارد — اما
  nginx این کار را نمی‌کند، و یک پیکربندی دست‌نویس nginx که
  `proxy_set_header Upgrade $http_upgrade;` را ندارد دقیقاً همین نشانه را می‌سازد. اگر Caddy را
  عوض کرده‌اید، ایراد همین است.
- **`server_url` با نشانی‌ای که کلاینت استفاده کرده فرق دارد.** باید نویسه‌به‌نویسه یکی باشند،
  شامل scheme و نبودِ اسلش پایانی. `https://hs.example.com` و `https://hs.example.com/` اینجا دو
  مقدار متفاوت‌اند.
- **کلید قبلاً استفاده شده است.** کلید بدون `--reusable` یک گره را یک‌بار ثبت می‌کند. در
  `headscale preauthkeys list` مقدار `Used: true` دیده می‌شود. یکی دیگر صادر کنید.
- **کلاینت خیلی قدیمی است.** نسخهٔ v0.29.3 به کلاینت Tailscale نسخهٔ v1.80.0 یا بالاتر نیاز دارد.
- زنده ببینیدش: هنگام اتصال کلاینت، `docker compose logs -f headscale`.

### خطاهای گواهی

کدام گواهی؟ بخش ۵. پیش از هر عیب‌یابی این را روشن کنید.

*اگر مرورگر از `headscale.example.com` شکایت دارد، یا کلاینت‌ها خطای TLS روی کنترل‌پلین می‌دهند:*

- `docker compose logs caddy`. Caddy صریح می‌گوید سرور ACME چه جوابی داده است.
- پورت ۸۰ باید از اینترنت در دسترس باشد. از جایی بیرون از VPS بررسی کنید، نه از خود VPS.
- رکورد A باید به همین VPS اشاره کند. `dig +short headscale.example.com` را از ماشینی غیر از VPS
  بگیرید.
- اگر چند بار پشت سر هم شکست خورده‌اید، ممکن است حدود یک هفته توسط Let's Encrypt محدود شده باشید.
  در `Caddyfile` خط `acme_ca … acme-staging-v02 …` را از توضیح خارج کنید، جریان را روی staging
  درست کنید (که گواهی‌اش را مرورگر رد می‌کند و همین انتظار می‌رود)، بعد دوباره توضیحش کنید.

*اگر مرورگر از `localcast.…` شکایت دارد:* آن گواهی ب است و این بخش شاملش نمی‌شود. به «نشانهٔ
مشخص راهبرد گواهی اشتباه» در پایین بروید.

### انحراف ساعت

هم دست‌دهیِ WireGuard و هم TLS، برچسب‌های زمانی خیلی دور را رد می‌کنند. VPS‌ای که ساعتش رانش کرده
ثبت‌نام‌هایی تولید می‌کند که با خطای امضا یا اعتبار گواهی شکست می‌خورند، و هیچ‌کدام از این خطاها
نام مشکل واقعی را نمی‌برند.

</div>

```bash
timedatectl status          # می‌خواهیم: "System clock synchronized: yes"
sudo timedatectl set-ntp true
```

<div dir="rtl">

ماشین ویندوز را هم بررسی کنید. معمولاً VPS بعد از suspend/restore مقصر است، اما نه همیشه.

### انقضای کلید

دو انقضای متفاوت، و اشتباه گرفتنشان یک بعدازظهر را هدر می‌دهد.

- **انقضای کلید پیش‌احراز** (`--expiration`، پیش‌فرض `1h`) — تا کی می‌توان با آن کلید گرهٔ جدیدی را
  *ثبت* کرد. وقتی گره ثبت شد، کلید دیگر برایش بی‌ربط است. کلید منقضی فقط روی ثبت‌نام‌های جدید اثر
  دارد: `authkey expired`.
- **انقضای کلید گره** — تا کی یک گرهِ ثبت‌شده معتبر می‌ماند. فایل `config.yaml` این پوشه مقدار
  `node.expiry: 0` را می‌گذارد، یعنی گره‌ها خودبه‌خود منقضی نمی‌شوند، دقیقاً برای اینکه LocalCast
  یک سه‌شنبهٔ آرام از شبکه غیب نشود. اگر تغییرش داده‌اید، گرهٔ منقضی در `headscale nodes list` با
  `Expired: true` دیده می‌شود و در حالی که هنوز فهرست شده ترافیک عبور نمی‌دهد. راه‌حل:
  `headscale nodes expire -i <ID> --disable` تا انقضا برای آن گره خاموش شود، یا احراز دوبارهٔ
  کلاینت.

### نشانهٔ مشخص راهبرد گواهی اشتباه

این یکی ارزش دارد که در نگاه اول بشناسیدش، چون وقتی رخ می‌دهد بقیهٔ چیزها سالم به نظر می‌رسند: گره
متصل است، `headscale nodes list` بی‌عیب است، و برنامه کار نمی‌کند.

| چه می‌بینید | یعنی چه |
|---|---|
| LocalCast روی «در حال دریافت گواهی» می‌ماند و بیرون نمی‌آید | `certStrategy` برابر `dns01` است اما توکن API دی‌ان‌اس اشتباه است، دامنهٔ دسترسی‌اش خیلی تنگ است، یا برای zone دیگری است. LocalCast عمداً به گواهی خودامضا عقب‌نشینی نمی‌کند، چون گواهی خودامضا روی iOS به‌جای خطا، یک اتصال WebDAV خراب و یک پخش‌کنندهٔ ویدیوی توضیح‌ناپذیر تولید می‌کند. |
| Safari: «This Connection Is Not Private» روی `localcast.…` | `external-proxy` را انتخاب کرده‌اید اما **مستقیم** روی شبکهٔ خصوصی به LocalCast وصل می‌شوید، نه از راه پروکسی. HTTP ساده روی نشانی شبکهٔ خصوصی سرو می‌شود و معنی `external-proxy` دقیقاً همین است. از طریق `certDomain` وصل شوید، نه از راه نشانی `100.x` یا نام MagicDNS. |
| صفحه روی HTTP باز می‌شود اما PWA نصب نمی‌شود و دوربین برای اسکن QR باز نمی‌شود | همان علت. سرویس‌ورکر و `getUserMedia` به بستر امن نیاز دارند. iOS در این مورد کوتاه نمی‌آید. |
| `certDomain` با نامی که مرورگر خواسته نمی‌خواند | گواهی معتبر است اما برای نام دیگری. با `dns01`، مقدار `certDomain` باید `<hostname>.<base_domain>` باشد — یعنی `localcast.net.example.com`. با `external-proxy` باید همان نام عمومی‌ای باشد که پروکسی سرو می‌کند — یعنی `localcast.example.com`. استفاده از نام `dns01` برای `external-proxy` یا برعکس، روی یک گواهی کاملاً سالم هشدار عدم تطابق نام می‌دهد. |
| ذخیره با پیام «Headscale cannot issue certificates through the control plane» رد می‌شود | هنگام رفتن به حالت شخصی، راهبرد را روی `control-plane` رها کرده‌اید. این ترکیب نمی‌تواند کار کند؛ بخش ۱ را ببینید. |
