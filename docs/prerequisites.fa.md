# پیش‌نیازهای LocalCast

**English version: [prerequisites.md](prerequisites.md)**

هر چیزی که LocalCast لازم دارد و `npm install` آن را برایتان فراهم نمی‌کند: اینکه چیست، چرا
لازم است، از کجا بفهمید روی این ماشین هست یا نه، و دقیقاً چه دستوری را اجرا کنید.

از یک کلون تازه:

```bash
npm install     # ماژول‌های بومی را هم برای Electron بازسازی می‌کند — بخش ۲
npm run doctor  # می‌گوید چه چیزی کم است و هرکدام را چطور درست کنید
npm start       # همه‌چیز را می‌سازد و برنامهٔ دسکتاپ را اجرا می‌کند
```

| # | پیش‌نیاز | اگر نباشد |
|---|----------|-----------|
| ۱ | Node نسخهٔ ۲۲ به بالا و npm | هیچ‌چیز ساخته نمی‌شود |
| ۲ | بازسازی `better-sqlite3` برای Electron | برنامه بالا می‌آید و سرِ اولین تماس با پایگاه‌داده می‌میرد |
| ۳ | Go نسخهٔ ۱.۲۳ به بالا، برای ساختن `netedge.exe` | **هیچ دسترسی‌ای از بیرونِ شبکهٔ محلی وجود ندارد** |
| ۴ | `SumatraPDF.exe` در `vendor/bin` | همه‌چیز کار می‌کند جز چاپ |

از این چهار مورد فقط شمارهٔ ۳ چیزی است که معمولاً روی ماشین کسی نصب نیست، و اتفاقاً مهم‌ترینشان
هم همان است.

---

## ۱. Node نسخهٔ ۲۲ یا بالاتر، و npm

**چیست.** همان زمان اجرای جاوااسکریپت که تمام این پروژه با آن ساخته می‌شود. npm همراه خودش
نصب می‌شود.

**چرا LocalCast به آن نیاز دارد.** سرور، هر دو برنامهٔ Electron و PWA همگی پروژه‌های Node
هستند و در یک workspace واحد npm قرار دارند. مقدار `engines.node` روی `>=22` تنظیم شده و
فایل‌های پیکربندی Vite از `import.meta.dirname` استفاده می‌کنند که روی نسخه‌های قدیمی‌تر اصلاً
وجود ندارد؛ روی Node 18 خطایی که می‌بینید شبیه یک فایل پیکربندی خراب به نظر می‌رسد، نه شبیه
یک Node قدیمی.

**چطور بفهمید دارید.**

```bash
node --version   # باید v22 یا بالاتر باشد
npm --version    # باید ۱۰ یا بالاتر باشد
```

**چطور تهیه‌اش کنید.** نسخهٔ LTS جاری را از <https://nodejs.org/en/download> نصب کنید. روی
ویندوز، نصب‌کنندهٔ `.msi` هم npm را می‌آورد و هر دو را روی `PATH` می‌گذارد. اگر چند نسخهٔ Node
دارید، پیش از کار در این مخزن `nvm use 22` را اجرا کنید.

## ۲. بازسازی ماژول بومی

**چیست.** ‏`better-sqlite3` یک افزونهٔ ++C است، نه جاوااسکریپت: یک فایل `.node` کامپایل‌شده.
هر افزونهٔ کامپایل‌شده برای یک نسخهٔ مشخص از رابط باینری (همان `NODE_MODULE_VERSION`) ساخته
می‌شود و فقط در زمان اجرایی بار می‌شود که دقیقاً همان شماره را داشته باشد.

**چرا LocalCast به آن نیاز دارد.** دستور `npm install` این افزونه را با رابط باینریِ همان
Node‌ای می‌سازد که نصب را اجرا کرده است — یعنی ۱۲۷ برای Node 22. اما برنامهٔ دسکتاپ روی آن Node
اجرا نمی‌شود؛ روی Electron 33 اجرا می‌شود که رابط باینری ۱۳۰ را در خود دارد. پس ماژولی که همین
الان ساخته شد، به دردِ زمان اجرایی که باید بارش کند نمی‌خورد و برنامه به‌محض باز کردن
پایگاه‌داده می‌میرد:

```
Error: The module '\\?\C:\...\node_modules\better-sqlite3\build\Release\better_sqlite3.node'
was compiled against a different Node.js version using
NODE_MODULE_VERSION 127. This version of Node.js requires
NODE_MODULE_VERSION 130. Please try re-compiling or re-installing
the module (for instance, using `npm rebuild` or `npm install`).
```

**به خط آخر همین پیام اعتماد نکنید.** دقیقاً همان `npm install` و `npm rebuild` بودند که ماژول
را روی ۱۲۷ گذاشتند؛ اجرای دوبارهٔ هرکدام فقط دوباره آن را برای Node می‌سازد و سرِ جای اولش
برمی‌گردید. این افزونه باید برای **Electron** ساخته شود.

**چطور بفهمید درست است.**

```bash
npm run doctor
```

وقتی همه‌چیز درست باشد می‌نویسد `better-sqlite3  built for Electron 33.4.11 (ABI 130)` و وقتی
نباشد، هر دو شماره را کنار هم نشان می‌دهد.

**چطور درستش کنید.**

```bash
npm run rebuild:native
```

این دستور `@electron/rebuild` را روی ماژول‌هایی که لازم دارند اجرا می‌کند و نسخهٔ Electron را
از خودِ بستهٔ نصب‌شده می‌خواند، نه از عددی که کسی توی اسکریپت تایپ کرده باشد — یعنی ارتقای
Electron دوباره همین مشکل را بی‌سروصدا برنمی‌گرداند. اگر ماژول از قبل درست باشد هیچ کاری
نمی‌کند، و به همین دلیل است که `npm start` هر بار آن را صدا می‌زند.

در حالت عادی اصلاً نباید درگیر این ماجرا شوید: اسکریپت `postinstall` در ریشهٔ مخزن همین کار را
انجام می‌دهد، پس یک `npm install` تازه درختی به شما می‌دهد که قابل اجراست. اگر بازسازی شکست
بخورد، `postinstall` عمداً نصب را ناموفق **نمی‌کند** و فقط می‌نویسد بعد از رفع مشکل چه دستوری را
اجرا کنید؛ چون کسی که این مخزن را فقط برای اجرای `npm test -w @localcast/server` کلون کرده
است نباید گروگانِ ابزارهای ساخت دسکتاپ شود.

**اگر بازسازی شکست خورد،** معمول‌ترین علت روی ویندوز این است که برای این ترکیبْ باینری از پیش
ساخته‌شده‌ای وجود ندارد و ماژول باید از روی کد منبع کامپایل شود؛ برای این کار به
Visual Studio **Build Tools** با بستهٔ *Desktop development with C++* نیاز دارید:
<https://visualstudio.microsoft.com/downloads/>. نصبش کنید، یک ترمینال تازه باز کنید تا
`PATH` به‌روز شود و دوباره `npm run rebuild:native` را بزنید.

**نسخهٔ بسته‌بندی‌شده اصلاً این مشکل را ندارد.** ‏`electron-builder` ماژول‌های بومی را هنگام
بسته‌بندی خودش بازسازی می‌کند، پس LocalCastِ نصب‌شده هرگز با این خطا روبه‌رو نمی‌شود. این
گرفتاری فقط مالِ اجرا از روی کد منبع است.

## ۳. Go نسخهٔ ۱.۲۳ یا بالاتر

**چیست.** زنجیرهٔ ابزار Go، برای کامپایل کردن `native/netedge` به `netedge.exe`.

**چرا LocalCast به آن نیاز دارد — این یکی را حتماً بخوانید.** ‏`netedge` لبهٔ شبکهٔ LocalCast
است: یک گرهٔ WireGuard در فضای کاربر (`tailscale.com/tsnet`) که TLS را روی tailnet پایان
می‌دهد و درخواست‌ها را به سرور Node روی لوپ‌بک پروکسی می‌کند. **بدون آن هیچ دسترسی‌ای از بیرونِ
شبکهٔ محلی وجود ندارد** — نه tailnet، نه گواهی، نه گوشی‌ای که از روی دیتای همراه وصل شود، نه
چاپ از ساختمان دیگر. یعنی عملاً بیشترِ محصول. برنامه باز می‌شود، پوشه‌ها را نشان می‌دهد و
می‌گوید چه چیزی درست نیست — چون پنلی که نتواند وضعیت خودش را توضیح دهد از پنلی که یک قابلیت
کم دارد بدتر است — ولی هیچ دستگاهی از بیرونِ این ماشین به آن نمی‌رسد.

Go فقط برای **تولید** آن فایل لازم است. وقتی `netedge.exe` ساخته شد، LocalCast روی ماشینی که
هیچ Go‌ای ندارد هم اجرا می‌شود؛ کاربر نهایی هم هرگز Go نصب نمی‌کند، چون نصب‌کننده همان باینریِ
کامپایل‌شده را با خودش می‌برد.

**چطور بفهمید دارید.**

```bash
go version                     # go1.23 یا بالاتر
ls native/netedge/netedge.exe  # باینری ساخته‌شده
```

‏`npm run doctor` هر دو را بررسی می‌کند و اگر باینری موجود باشد، نبودِ Go را فقط یک یادداشت
می‌داند نه یک مشکل.

**چطور تهیه‌اش کنید.** Go را از <https://go.dev/dl/> نصب کنید (نصب‌کنندهٔ `.msi` ویندوز دستور
`go` را روی `PATH` می‌گذارد؛ بعدش یک ترمینال تازه باز کنید) و بعد:

```bash
npm run netedge:build   # go build -o netedge.exe ./cmd/netedge
npm run netedge:test
```

اولین ساخت در یک کلون تازه باید نسخهٔ وابستگی‌ها را هم حل کند: فایل `go.mod` بدون در دسترس
بودن زنجیرهٔ ابزار نوشته شده و هنوز `go.sum` وجود ندارد. دستور دقیق `go get` برای این کار در
`native/netedge/README.md` آمده است، و همان‌جا توضیح داده شده که بعدش باید دنبال کامنت‌های
`VERIFY:` بگردید.

## ۴. ‏SumatraPDF در `vendor/bin`

**چیست.** یک نمایشگر و چاپگر PDF کوچک و قابل حمل. LocalCast آن را به‌عنوان یک فرایند جداگانه
صدا می‌زند تا کارهای چاپ را تحویل ویندوز بدهد.

**چرا LocalCast به آن نیاز دارد.** کار چاپ با سوئیچ‌های `-print-to` و `-print-settings` همین
برنامه ثبت می‌شود و بعد وضعیتش از صف چاپ واقعی ویندوز خوانده می‌شود. همراه بردنش همان چیزی
است که باعث می‌شود چاپ از راه دور مستقل از اینکه کاربر چه نمایشگر PDF‌ای دارد کار کند. عمداً
داخل این مخزن کامیت نشده است: یک فایل اجرایی طرف‌سومِ کامیت‌شده هم مسئلهٔ مجوز است و هم مسئلهٔ
بازبینی، و دانلود خودکارش هنگام ساخت یک مسئلهٔ زنجیرهٔ تأمین.

هیچ بخش دیگری به آن وابسته نیست. بدون آن مرور فایل‌ها، پخش ویدیو، WebDAV و آپلود همگی عادی کار
می‌کنند و یک کار چاپ با پیام «کمکیِ چاپ موجود نیست» شکست می‌خورد، به‌جای اینکه وانمود کند کار
در صف نشسته است.

**چطور بفهمید دارید.**

```bash
ls vendor/bin/SumatraPDF.exe
node scripts/verify-vendor.mjs
```

**چطور تهیه‌اش کنید.** نسخهٔ **portable ۶۴ بیتی** را از سایت رسمی
<https://www.sumatrapdfreader.org/download-free-pdf-viewer> بگیرید و در مسیر
`vendor/bin/SumatraPDF.exe` بگذارید. بعد، یک‌بار، اثر انگشتش را ثبت کنید:

```bash
node scripts/verify-vendor.mjs --record
```

این دستور SHA-256 همان فایلی را که واقعاً دانلود کرده‌اید در `vendor/checksums.json`
می‌نویسد، تا اجراهای بعدی و CI بتوانند ثابت کنند باینری زیر دستتان عوض نشده است. **پیش از
ثبت**، این اثر انگشت را با چک‌سامی که خود پروژهٔ SumatraPDF منتشر می‌کند مقایسه کنید:
سوئیچ `--record` به هر فایلی که جلویش باشد اعتماد می‌کند، و چک‌سامی که با مرجع مقایسه نشده
باشد هیچ چیزی را ثابت نمی‌کند. شرایط مجوز در `vendor/README.md` توضیح داده شده است.

## دستورها

| دستور | چه می‌کند |
|-------|-----------|
| `npm install` | وابستگی‌ها را نصب و بعد ماژول‌های بومی را برای Electron بازسازی می‌کند |
| `npm run doctor` | همهٔ موارد این صفحه را بررسی می‌کند؛ اگر چیزی بازدارنده کم باشد با کد ناصفر خارج می‌شود |
| `npm start` | بررسی بازسازی ← ساخت کامل ← اجرای برنامهٔ دسکتاپ |
| `npm run dev` | ‏Vite برای رابط Electron (`:5174`) و برای PWA (`:5173`)، به‌همراه Electron که به اولی وصل می‌شود |
| `npm run rebuild:native` | فقط بازسازی ماژول بومی |
| `npm run netedge:build` | ساخت سایدکار Go (نیازمند Go) |
| `npm run build` / `npm test` | کل workspace |

دستور `npm run dev` مقدار `VITE_DEV_SERVER_URL` را روی سرور توسعهٔ رابطِ **دسکتاپ** می‌گذارد؛
همان چیزی که فرایند اصلی می‌خواند تا پنجره را از Vite بار کند نه از روی دیسک. سرور توسعهٔ PWA
هم کنارش بالا می‌آید، چون در حالت توسعه سرور Node نسخهٔ ساخته‌شدهٔ PWA را سرو نمی‌کند و این کار
با Vite انجام می‌شود. پروکسی `/api` و `/dav` در PWA به `LOCALCAST_DEV_API` نگاه می‌کند که
به‌طور پیش‌فرض `:8420` است؛ چون برنامهٔ دسکتاپ روی یک پورت گذرا گوش می‌دهد، اگر می‌خواهید این دو
با هم حرف بزنند باید آن متغیر را دستی تنظیم کنید.
